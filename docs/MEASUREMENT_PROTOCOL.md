# 测量协议与统计纪律 / Measurement Protocol & Statistical Discipline

> 本文是 `README.md` §3 的完整版：定义本仓库所有数字的口径、采样与判定规则。任何新增实验（含后续补格）必须遵循本协议，否则数据不并入结论。

## 1. 指标定义

| 指标 | 定义 | 分母 | 采集端点 |
|---|---|---|---|
| **TPOT / t_tok** | 每输出 token 时延 = `(elapsed − TTFT) / completion_tokens` | **实测输出 token 数**（禁止使用 `max_tokens`） | 客户端，**非流式** |
| **t_iter** | 每轮引擎迭代成本 = `(elapsed − TTFT) / Δiters` | 服务端 SpecDecoding 计数差分得到的迭代数 | 服务端日志窗口 |
| **聚合吞吐** | `Σ completion_tokens / wall_clock` | — | 客户端 |
| **单用户吞吐** | 聚合吞吐 / 并发数（随并发单调下降） | — | 客户端 |
| **接受长度 acc** | `completion_tokens / ΔDrafted`；等价于服务端 `1 + Accepted/Drafted` | 草稿 token 数 | 服务端计数差分 |
| **逐位置接受率** | 服务端 `Per-position acceptance rate`（其定义即链式接受率 `γ_i = Π_{j≤i} α_j`） | 草稿次数 | 服务端日志 |

**关键性质**：vLLM 每个指标窗口都会打印逐位置接受率，因此 **α 链的测量成本为 0**——任何一次运行的日志里都有。但**必须在固定 K 下读取**：动态 K 时高位位置不被草稿，其计数被掩码而低估。

## 2. 双口径互证规则

1. 外部口径（非流式墙钟）与内部口径（服务端计数差分）必须**同时**给出一致方向与量级（本仓库容忍 ±3%）。
2. 两口径矛盾时，**引入第三口径仲裁**（例如服务端 `Avg generation throughput` 窗口值），禁止通过调整配置把矛盾拟合掉。
3. 任何性能结论必须能立即回答四件事：**负载形状、并发、基线定义、计时口径**。缺一项则不得写入结论。

## 3. 已知测量陷阱（本项目全部实际踩过）

| # | 陷阱 | 症状 | 对策 |
|---|---|---|---|
| 1 | 流式客户端成本单侧计入 | 实验臂 TPOT 虚增 ~19 ms/迭代，基线不受影响 ⇒ 误判"投机解码负收益" | 一律使用**非流式**请求；流式客户端只用于同路径相对比较 |
| 2 | EOS 早停使分母漂移 | 同一 prompt 实际输出 140（上限 256），轮间抖动 | 分母用 `completion_tokens`；报告中记录其分布 |
| 3 | 指标计数器按窗口清零 | 跨窗口差分得到 acceptance=25.6 等荒谬值 | 先验证计数器语义（累计 or 窗口），再做差分；小样本窗口不单独作结论 |
| 4 | 臂间残留进程/缓存 | 下一次启动在图捕获阶段随机失败 | 通杀 `spawn_main\|EngineCore\|vllm`，等待并以 `npu-smi` 确认"无进程" |
| 5 | 固定 `sleep` 等待服务就绪 | 客户端撞 `Connection refused` | `/health` 轮询（图捕获时长会漂移） |
| 6 | 多臂共享同一日志文件 | 故障现场被后一臂覆盖，root cause 丢失 | **每臂独立日志文件** |
| 7 | 手设参数与自动推导冲突 | 覆盖守卫静默回退，收益丢失且看似正常 | 参数化后必须校验推导值（例：档位上限须 ≥ 各档 `最大批 × span` 向上取整到档位） |
| 8 | 以"看起来合理的解释"替代读栈 | 多轮无效尝试 | 结论必须有 traceback / 错误码 / trace 差分支撑 |

## 4. 采样设计

- **锚点优先**：先测两个端点（串行 = 最低延迟；饱和并发 = 最高吞吐），再在内插点取样（vLLM 官方 sweep 协议）。
- **批尺寸取 2 的幂且必含上下限**：本仓库为 `{1, 4, 16, 64}`（FMwork 协议）。
- **输出长度 128 token 足以刻画性能空间**（FMwork：对 1024 的保真度 96.6%）。
- **每格 3 轮取中位数**；剔除 warmup；轮间变异 >5% 时加测。本项目的重复性噪声带实测为 **±0.7 ms/token**。
- **同会话内交错执行**（A,B,A,B）以抵消热漂移；换臂必须重启服务并清卡。
- 投机解码专属：**acceptance 与 speedup 必须并列报告**（差分口径），并给出 break-even 判据；每个臂记录 `completion_tokens` 分布。

## 5. 判定阈值（写入结论的门槛）

| 场景 | 判定为"有收益"的条件 |
|---|---|
| 吞吐类 | Δ ≥ 3× 噪声带，且两口径同向 |
| 时延类 | Δ ≥ 1.5× 噪声带（本仓库 1.5×0.7 ≈ 1.0 ms/token），且两轮独立重复同向 |
| 归因类 | 必须有 trace 差分或 per-site 计时数据，不接受由算子名推测 |
| 负结果 | 同样必须给数据（例：§6.3 的"跳过同步零收益"给出 K=1/K=3 两组区间） |

## 6. 报告结构规范（本仓库 README 即按此组织）

环境块 → 方法块（含每个指标的**定义与分母**）→ 主表（含 Δ vs 基线列）→ 图（饱和曲线、加速热图、延迟-吞吐 Pareto）→ 机制解释 → 优化与量化结论（含负结果）→ 边界/失效判定 → 复现指南 → **Threats to validity** → 附录与参考。

## 7. 可复用检查清单

- [ ] 两个锚点（串行 + 饱和并发）都测了？
- [ ] 并发取 2 的幂且含上下限？
- [ ] 负载至少两种形状（当前缺：长入短出、长输出）？
- [ ] 每格 ≥3 轮、取中位、剔除 warmup、变异 <5%？
- [ ] 每个数字的分母写显式了吗（`completion_tokens`，不是 `max_tokens`）？
- [ ] 投机解码：acceptance 并列报告了吗？两口径一致吗？α 链在固定 K 下读取了吗？
- [ ] 臂间清了状态（进程 / 设备 / 缓存）并交错执行了吗？
- [ ] 环境与 commit 锁定并 dump 了吗？
- [ ] 写了 threats to validity 吗？
- [ ] 负结果是否也给到了数据支撑？
